---
description: Co-author a PRD with the product owner from a BRD/Jira/free-text source. Conversational and section-by-section. Surfaces tribal knowledge the BRD does not capture, lets the PO reason through design choices, and publishes one Confluence PRD per user journey. Feeds /sp.backlog and /sp.pdlc.
---

## Usage

```
/sp.prd "brief"
/sp.prd --jira PROJ-123
/sp.prd --confluence <pageId>
/sp.prd --confluence <pageId> --name "PRD-02-01"
/sp.prd --confluence <pageId> --single-prd
/sp.prd ... --full
```

| Flag | Meaning |
|------|---------|
| `--jira` / `--ticket` / `-j` | `getJiraIssue` |
| `--confluence` | `getConfluencePage` markdown |
| `--name` | First `PRD-BB-MM`; auto-increment siblings |
| `--single-prd` | Force **one** Confluence doc when the agent would otherwise split a single journey |
| `--full` | Longer narrative in sections where the template allows prose. Same section structure and style as the default; no compression at publish time. |

**Defaults:** A BRD may yield **K PRDs** only when slices are **independently shippable** or **ownership/context** differs. **One user journey** (e.g. the same list screen with **filter + search** together) maps to **one PRD**; do **not** split into separate PRDs per control unless the BRD explicitly separates scope. **`--single-prd`** forces one doc when the agent would otherwise over-split. The Confluence body always follows the active `prd-template.md` structure -- see **PRD shape and writing style** below.

## User Input

```text
$ARGUMENTS
```

Must honor non-empty `$ARGUMENTS`.

## Philosophy: PO is the expert, agent is the facilitator

The product owner knows things about the product, users, business rules, history, and constraints that **no BRD or codebase captures**. This command's job is to surface that **tribal knowledge** through structured conversation -- not to replace the PO with autogenerated guesses. The PRD is co-authored, not delivered.

| Principle | Implementation |
|-----------|----------------|
| **Always use `AskUserQuestion`** | For any decision with material impact on scope, behavior, persona, or acceptance. Never assume; never silently fill gaps. |
| **Suggest, don't interrogate** | Every question opens with a **recommended option and a one-line rationale**, then an options table (2-4 choices), then a free-text escape ("or specify"). Make it cheap for the PO to confirm rather than think from scratch. |
| **One concept at a time** | Walk the PRD section by section. Ask, draft, confirm, move on. Do **not** batch all questions upfront and do **not** dump a full PRD for a single approval at the end. |
| **Skip when answered** | If the BRD / Jira / linked source already answers a question, do not re-ask. Use what is on the page and move on. |
| **Capture decisions, not just facts** | When the PO chooses between options, record the choice and a one-line rationale (in the PRD section it affects, or as a `[DECISION NEEDED]` if it remains open) so future readers know **why**. |
| **Code grounding is optional** | When the `context-stack` MCP is available, use it lightly to verify named services / paths / NFR targets. When it is not -- the typical PO setup -- tag implementation claims for engineering verification or move them to **Known Gaps**. |
| **Lightweight** | Cap the conversation at **6 to 8 high-impact questions** for a normal PRD. If the source is rich, ask fewer. The PO is busy. |

(Inspired by the Agent OS `discover-standards` philosophy: extract tribal knowledge through targeted, human-in-the-loop conversation; let the human decide what to keep; suggest before asking; one concept at a time.)

## Persona & token economy

Senior PO co-author: WHAT/WHY, testable reqs, explicit rules, measurable success. **Do not** paste BRD walls into chat; emit a **compact session summary** after the first big fetch. **Links** over bodies in completion output. The agent's voice in the PRD is plain English; in the chat the agent is a collaborator, not autopilot.

## One PRD = one feature *(one journey, possibly multiple mechanics)*

| Rule | Requirement |
|------|-------------|
| Scope | One **primary user goal / journey** per PRD. Multiple **mechanics** on the same journey (e.g. **optional filter** and **optional search** on **My Orders**) stay **in the same PRD** -- one requirements table, one AC set, one publish. |
| BRD | Many **distinct** capabilities or domains map to many PRDs. Do **not** mint separate PRDs for each UI control when the BRD describes one incremental list experience. |
| Header | `Related PRDs:` + Confluence URLs when siblings exist. |
| Split if | Distinct journeys, different owning service/context, different shippable stories, or a BRD feature matrix that **explicitly** lists independent delivery slices. Length alone is **not** a reason to split. |
| One doc OK | Single cohesive journey (including filter+search-style bundles) or `--single-prd`. |

## PRD shape and writing style

**Goal:** One Confluence page that is **PO-complete and easy to read**. The body must look like a product document a stakeholder can pick up cold -- not a digest, not a table dump, not a glyph soup.

| Rule | Requirement |
|------|-------------|
| **Template is authoritative** | Follow `.specify/templates/prd-template.md` **exactly**: same section order, same section names, same prose-vs-table conventions. Do **not** invent a parallel section scheme, do **not** renumber, do **not** drop or merge sections without an explicit reason. |
| **Match the template's prose-to-table ratio** | If the template renders a section as narrative paragraphs (Problem Statement, User Persona, What It Does, How It Works), write **paragraphs** -- not bullet fragments and not tables. Use tables **only** in the sections where the template uses tables (Business Rules, UI, Edge Cases, NFRs, Dependencies, Files, Known Gaps, Success Indicators). |
| **Writing style** | Full sentences in plain English. The body should read like a product document a stakeholder can pick up cold. Use abbreviations only when they are **widely understood in software product writing** (e.g. API, UI, HTTP, gRPC, SLO, P0/P1/P2); spell out anything that is project-specific or that a non-engineer might not recognise (write "out of scope" instead of `OOS`, "version 1" instead of `v1` in narrative prose, etc.). Spell out boolean logic in prose ("any of the selected statuses"; "matches both the search term and the status filter"); do not substitute logic or math glyphs for words. Refer to sections by name or number ("see Section 7"); do not use the section-sign glyph. **ASCII-only in the body** -- avoid logic glyphs, math glyphs, smart quotes, smart dashes, non-breaking spaces, and any other characters outside the printable ASCII range; use the plain-text equivalents (`-`, `"..."`, `'`, `<=`, `->`, `~=`, `--`). Examples are illustrative, not exhaustive -- the rule is "ASCII only" everywhere except code identifiers in backticks. |
| **Size** | Soft cap: **12 to 20 KB UTF-8** for the markdown `body` (a normal PRD is several pages). Do **not** abbreviate sentences or strip vowels to fit. If a single section is genuinely bloated, tighten **that** section; if the whole feature is too large, the answer is to **split into multiple PRDs** (see **One PRD** rules above), not to compress. |
| **`--full`** | Same shape as default; just longer narrative where the template allows prose. Still ASCII-safe and still one section structure. |
| **Single MCP upload** | Use **exactly one** Confluence **write** MCP call per PRD delivered in the run: **`createConfluencePage`** (new page) **or** **`updateConfluencePage`** (replace body on an existing page the user pointed at or a duplicate title match). Do **not** chain create + update to "finish" the same PRD; **not** multiple updates; prepare the **final** markdown **before** that single call. Retries after tool/network failure are OK (same intent, one successful write). |
| **Publish** | **New:** **`createConfluencePage`** with the full body (no H1 duplicate of title), correct `parentId`, `contentFormat: markdown`. **Existing page refresh / user-supplied id:** **`updateConfluencePage`** with the same constraints. Do **not** use update as a second step after create for the same content in one run. |
| **Split vs shorten** | Prefer **one PRD** when the BRD describes one buyer journey (e.g. filter + search on the same list). **Split** when capabilities are independently shippable or ownership differs -- never to fit a size cap. |

## Storage

- **SoT:** Confluence (`createConfluencePage` / `updateConfluencePage`). No new `docs/prds/**` or `docs/brds/**`.
- **Drafts:** `docs/.specify-staging/prd|brd/*.md` (gitignored). **Delete** after successful publish; **WARN** + keep if publish skipped/failed.
- Titles: `<PRD-ID>: <Feature>`, `BRD-NN: <Domain>`.

## Inputs

Combining `--jira` and `--confluence` is allowed. Fetch before drafting. No fetch and no usable text is an **ERROR**. Body structure always comes from the active `.specify/templates/prd-template.md` (do not crawl Confluence for layout).

## Grounding (`context-stack` MCP -- optional)

The typical PO setup does **not** include `context-stack` (zoekt + stackgraph + neo4j + dexter). **Do not gate** the workflow on it. When it **is** available (see [`.cursor/rules/context-stack.md`](../rules/context-stack.md)), use it lightly to verify implementation claims and find sibling docs that should be cross-linked. A couple of targeted lookups, not a survey.

| When | Tool (server: `context-stack`) |
|------|--------------------------------|
| Codebase orientation before drafting | `get_context("how does <domain> work today; key services + flows")` |
| Verify a specific symbol / RPC / file path the PRD will name | `search_code("<symbol or RPC name>")` |
| Find sibling PRDs/BRDs to cross-link in the header | `search_specs("<domain keywords>")` + `search_docs("PRD OR BRD <domain>")` |
| Master-spec capability bucket | `search_specs("master-spec <capability keyword>")` |

**Conflict rule (code wins over docs):** If a Confluence/BRD/Jira source describes a service, RPC, schema, or behavior that disagrees with what `search_code` / `get_context` shows in the actual codebase, **the code is the source of truth for "what is"**. Surface the gap in the PRD's **Known Gaps** section with both citations -- never silently parrot a stale doc.

**When `context-stack` is unavailable:** The PRD must still be **PO-complete on intent, scope, requirements, AC, business rules, and success indicators** -- those are the PO's domain and do not need code search. For **implementation-level** claims (specific service names, RPCs, file paths in Section 4 "How It Works" or Section 10 "Files"):

- Tag with `[ENG: verify]` inline, **or**
- Move to **Section 11 -- Known Gaps and Tech Debt** with a note that engineering will validate during `/sp.plan` or `/sp.hld-lld`.

Either way, never invent infrastructure. If the PO is unsure whether a service exists, label it **NEW** in the draft and confirm with them.

**Citation discipline:** Reference real paths inline only when needed; do **not** include `context-stack` result lists in the PRD body. The PRD reads as a product document, not a search transcript.

## Process

The flow is **conversational and section-by-section**. Do **not** generate a full PRD draft and then ask the PO to review it; co-author it instead. Use `AskUserQuestion` for every clarification; never poll the PO with free-text "what do you think?" prompts.

### Phase 0 -- Load sources and orient

1. Parse `$ARGUMENTS`. Identify Confluence pageId(s), Jira key(s), free-text brief. Combine if multiple.
2. Fetch the source via Atlassian MCP -- `getConfluencePage` (`contentFormat: markdown`) for BRD pages, `getJiraIssue` for tickets. **One** narrow Confluence fetch per id; **no** space-wide BRD crawl. BRD plus at most one canonical follow-up; siblings via narrow CQL `PRD-<BB>-*` only when needed for ID assignment.
3. Read the active **`.specify/templates/prd-template.md`** so the section list and prose-vs-table conventions are loaded before any drafting.
4. Skim **`.specify/memory/master-spec.md`** and **`.specify/memory/constitution.md`** if they exist (capability framing and policy gates).
5. (Optional) When `context-stack` is available, run **one** `get_context("<domain> services + flows")` to orient. Otherwise skip silently.
6. Emit a compact **session summary** in chat (5 to 10 lines): source label and URL, detected domain, suspected primary actor, suspected scope, any conflicts spotted between source and code (if `context-stack` was used). **Do not** paste BRD walls.

### Phase 1 -- Frame the PRD (scope and journey)

Use **`AskUserQuestion`** to confirm framing **before** any section drafting. For each item below, present a **recommended option with a one-line rationale**, an options table (2-4 choices), and a free-text escape. Do not advance until each is answered.

| Frame question | What to surface |
|----------------|-----------------|
| **Bounded context (domain)** | Detected domain (e.g. *Order Management*, *Identity and Authentication*, *Catalog*) plus 1-2 alternative readings if the BRD is ambiguous. Wrong context here breaks everything downstream. |
| **Primary user / persona** | Who is the PRD primarily for: anonymous buyer, signed-in buyer, operator, downstream service, etc. Note a secondary actor if relevant. |
| **One PRD or multiple slices?** | Default is one journey -> one PRD. Surface a split only when slices are **independently shippable** and **ownership differs**. Honor `--single-prd`. |
| **PRD ID and folder** | Detected/suggested `PRD-BB-MM` from a narrow Confluence sibling search; the **domain PRD folder** as `parentId` (never the BRD library folder). PO confirms or overrides. |

**Suggest-and-confirm pattern** (use this shape for **every** `AskUserQuestion` in this command):

```
[Section / topic]: [one-sentence framing of what is being decided]

**Recommended:** Option A -- [one-line rationale grounded in the BRD, a sibling spec, or a common pattern]

| Option | Description |
|--------|-------------|
| A      | [Recommended choice] |
| B      | [Alternative] |
| C      | [Alternative if it adds signal] |
| Other  | Provide a different short answer |

Reply with the option letter, "yes" / "recommended" to accept A, or your own short answer.
```

### Phase 2 -- Surface tribal knowledge (per PRD section)

The BRD usually answers **what** at a high level. The PO carries the rest. Walk the template **section by section** in numerical order. For each section:

1. Read what the source(s) say about it. If `context-stack` is available, optionally do **one** `search_specs("<topic>")` to see whether a sibling PRD already commits to a value.
2. Identify the **gaps** the section needs that the source does not cover (example: BRD says "filter by status" but does not name the statuses, the empty state, or precedence vs. an active search query).
3. If `context-stack` answered the gap, use it silently with a citation in the eventual draft. **Do not** consume the question budget on items already resolved.
4. Otherwise ask the PO **one question at a time** with the suggest-and-confirm pattern from Phase 1. Hard cap: **6 to 8 user-facing questions across the entire run** (Phase 1 + Phase 2 combined). If a section's gap is low impact, skip the question and let the draft fill a sensible default that the PO can edit in Phase 3.
5. Record the answer in working memory and move on. Do **not** revisit answered questions.

**Sections to walk and the typical tribal-knowledge gap a PO answers:**

| Template section | Tribal-knowledge gap to listen for |
|------------------|-------------------------------------|
| 1. Problem Statement | "Why now"; cost of doing nothing; segments most affected |
| 2. User Persona | Distinguishing behavior vs. other personas; auth state; device or channel constraints |
| 3. What It Does -- Happy Path | Concrete journey steps the BRD glossed over; what the user sees at each step |
| 3. What It Does -- Alternate Flows | Empty state, error state, blocked / partial-data state, downgrade path |
| 4. How It Works *(if PO has hints)* | Reuse vs. new; named services or RPCs the PO expects; data sources |
| 5. Business Rules | Priorities, exclusions, regional or segment differences, kill-switch behavior |
| 6. UI Requirements *(if applicable)* | Components, copy, behavior under load; Figma frames if any |
| 7. Edge Cases | Concurrency, conflicting inputs, downstream failures, permission edges |
| 8. Non-Functional | Latency targets, observability, reliability -- only if **this** feature has unusual needs |
| 9. Dependencies | Upstream services, data, decisions waiting on other teams |
| 10. Files / How It Works *(if applicable)* | What is reused vs. NEW |
| 11. Known Gaps | What we are knowingly deferring; why it is acceptable for now |
| 12. Success Indicators | What "shipped well" looks like 1-2 weeks after launch |

If the PO ever says "you decide" on something material, record the chosen value plus a one-line rationale, and add a `[DECISION NEEDED]` entry under the relevant section so the choice is explicit (cap **3** of these per PRD).

### Phase 3 -- Draft section by section (confirm each)

For each section in template order:

1. Draft the section using BRD content + Phase 2 answers. Match the template's prose-vs-table style: narrative paragraphs for Problem, Persona, What It Does, How It Works; tables for Business Rules, UI, Edge Cases, NFRs, Dependencies, Files, Known Gaps, Success Indicators. ASCII-only.
2. Show the draft to the PO with **`AskUserQuestion`**:

   ```
   Draft for Section N -- [Section Name]:

   [draft body, compact]

   | Option | Description |
   |--------|-------------|
   | Approve | Looks good, move on |
   | Edit    | I will tell you what to change |
   | Skip    | Mark this section N/A and renumber later |
   | Regen   | Regenerate with this hint: [PO supplies hint] |
   ```

3. Apply edits, finalize the section, move to the next. Keep individual section drafts **compact** -- the PO should be able to scan and approve in seconds.
4. If the PO chose **Skip**, mark the section omitted and renumber subsequent sections per the template's "Template notes" guidance.
5. Do **not** show the assembled full PRD until all sections are confirmed.

When `--full` is set, write **longer narrative** in prose sections (Problem, Persona, What It Does, How It Works); tables stay the same.

### Phase 4 -- Optional code grounding

Run **only** if `context-stack` is available. Otherwise skip and proceed to Phase 5; implementation-level claims should already carry `[ENG: verify]` tags or live in **Known Gaps** per the **Grounding** section above.

When `context-stack` is available, do a **light** verification pass:

- For service / RPC / file names in Section 4 "How It Works" and Section 10 "Files": one `search_code("<name>")` each. If not found, change the tag to **NEW** or move to **Known Gaps** -- confirm via `AskUserQuestion` before mutating the draft.
- For dependencies in Section 9: one `search_specs("<dep>")` per dependency to see if a sibling spec already commits to it; cross-link in the header `Related PRDs` if so.
- For NFR claims in Section 8: one `search_docs("<service> SLO OR runbook")` per claim; if a stricter target exists, surface to the PO ("Runbook says p95 < 200ms; PRD says < 500ms -- which holds?").

**Conflict resolution:** When code or runbook disagrees with a PO statement, ask the PO once via `AskUserQuestion` with three options: **keep PO version**, **adopt code/runbook**, or **record both as a Known Gap**. Do not silently overwrite the PO.

### Phase 5 -- Validate

Run the gates below before staging. Iterate up to **3** fix passes. If a gate still fails after 3 passes, **stop and surface the unresolved items to the PO** via `AskUserQuestion` rather than papering over them or splitting the PRD as a workaround.

**Structural gate**

- Bounded context confirmed in Phase 1; header populated; no invented infrastructure.
- At most **3** `[DECISION NEEDED]` items.
- One journey per PRD (mechanics bundled per the **One PRD** rules); extra slices only with `--single-prd` or a true multi-capability BRD.
- Every section the active `prd-template.md` defines is present, in the right order, with the right name. Sections explicitly N/A are removed and subsequent sections are renumbered consecutively.

**Writing-style gate**

- Narrative sections contain paragraphs (full sentences); tables only in sections where the template uses tables.
- Body is ASCII-only (no logic, math, or section glyphs; no smart quotes / dashes; no non-breaking characters).
- Abbreviations limited to the widely-understood software-product set; project-specific terms spelled out.
- No orphan labels: every table header has rows, every list has items, every section has body content.

**Acceptance gate**

- Each P0 requirement has at least one **Section 12 Success Indicator** row that an engineer can implement a test or probe for.
- Edge Cases table is non-empty for any user-facing feature.
- Section 3 Happy Path narrates the journey concretely (not "user does X, system does Y" abstractions).

### Phase 6 -- Publish

1. Stage the final PRD body to `docs/.specify-staging/prd/PRD-<BB>-<MM>-<kebab>.md` (and `brd/` if a new BRD was minted -- see **Legacy step** below).
2. Show the assembled PRD body to the PO with `AskUserQuestion`:

   ```
   Full PRD ready (NN KB). Final action?

   | Option | Description |
   |--------|-------------|
   | Publish    | Create or update the Confluence page under the domain PRD folder |
   | Edit       | Point me at sections to revise; I will loop back to Phase 3 |
   | Stage only | Keep the staging file; do not publish |
   ```

3. On **Publish**:
   - Resolve `parentId` -- the **domain PRD folder**, not the BRD library folder. Algorithm:
     1. From the source BRD, read **domain** (e.g. *Order Management*).
     2. Find any existing PRD in that domain in the same space (`getPagesInConfluenceSpace` / title prefix `PRD-` + domain keyword, or narrow CQL). Open it; set **`parentId` = that PRD's `parentId`** (the domain PRD folder).
     3. If no PRD exists yet: locate the space's PRD hierarchy and the folder for that domain (title aligned with domain), via space navigation. If it cannot be found, **stop** and ask the PO once for the correct PRD folder page id (do not fall back to the BRD page's `parentId` or the BRD library folder).
     4. **Validate** after create: the new PRD's `parentId` must equal a known domain PRD sibling's `parentId`, not the BRD page's `parentId`.
   - Use `searchConfluenceUsingCql` to check for a duplicate by title; ask the PO before overwrite.
   - Use **exactly one** Confluence write MCP call: `createConfluencePage` (new) or `updateConfluencePage` (existing). Body is markdown rendered per the active `prd-template.md`. **Do not** chain create + update for the same content in one run.
   - On success, delete the staging file. On failure, keep it and **WARN**.
4. Report BRD/PRD URLs and page ids. Suggest next: `/sp.backlog --confluence <id>`, `/sp.design` if Section 6 UI Requirements is non-empty, `/sp.pdlc`.

### Legacy step -- BRD creation when none exists

If the source is a Jira ticket or free-text brief and **no BRD exists** for the domain:

1. Confirm with the PO via `AskUserQuestion` whether to mint a new BRD first (recommended) or proceed PRD-only with a `[BRD: missing -- mint via /sp.brd-refine]` header tag.
2. If yes, draft a concise domain BRD; stage to `docs/.specify-staging/brd/BRD-NN-<kebab>.md`; create in Confluence under the BRD library folder (FKPOC `spaceId 490405892`); delete staging on success; reference the new BRD in the PRD header before continuing to Phase 1.

## Ambiguity

Domain first (ask in Phase 1). Then master-spec / constitution for **facts**, not domain choice. Resolve **product** ambiguity before drafting via the suggest-and-confirm `AskUserQuestion` pattern; capture **implementation** ambiguity as `[DECISION NEEDED]` items (cap 3) with an options table inside the relevant PRD section.
